# وثيقة معمارية الأدوار والصلاحيات — منصة مِهلة (RBAC Architecture)

> نطاق الوثيقة: طبقة التحكم بالوصول لكامل المنصة كشركة SaaS: فريق تشغيل مِهلة
> (Platform Staff) ومكاتب المحاماة العميلة (Tenants). هذه الوثيقة هي المرجع
> الملزم للمرحلة الثالثة، وأي تنفيذ يخالفها يُعد خطأً.
>
> المركز المالي **مُجمَّد** (Financial Module Freeze): لا يُعدَّل إلا لخطأ مثبت،
> متطلب جديد، أو تكامل جديد (Moyasar / ZATCA). ما يخص المركز المالي هنا توثيق
> للواقع الحالي لا دعوة لتعديله.

---

## 1) المبدأ الحاكم: فصل عالمين

المنصة تحتوي **مجالين منفصلين تماماً** للتحكم بالوصول، ولا يوجد جسر مباشر بينهما:

| المجال | الجهة | مصدر الهوية | مصدر الصلاحية | النطاق |
|---|---|---|---|---|
| **Platform Domain** | موظفو مِهلة | `platform_staff` | `platform_roles` + صلاحيات فردية | `/mehla-admin` |
| **Tenant Domain** | مكاتب المحاماة | `organization_members` | `app_role` داخل المكتب | `app.mehlalex.com` |

قاعدة الخصوصية الجوهرية (غير قابلة للتفاوض):

> **لا توجد ولن توجد صلاحية تمنح موظف مِهلة الاطلاع على بيانات المكاتب**
> (القضايا، المستندات، ملفات العملاء، الملاحظات، المرفقات).
> الاستثناء الوحيد: منحة **وصول دعم مؤقت** (`support_access_grants`) يوافق عليها
> المكتب نفسه، بنطاق محدد ومدة محددة وسبب مُسجَّل في سجل التدقيق.

## 2) هيكل الأدوار

### 2.1 أدوار المكتب (Tenant Roles) — ثابتة بالتصميم

`app_role`: `owner` → `admin` → `lawyer` → `legal_assistant` → `viewer`

هذه الأدوار **مقصودة الثبات**: مصفوفة صلاحيات المستندات والطباعة والبيانات
الحساسة مبنية عليها (`src/lib/doc-permissions.ts`)، وتغييرها يلمس RLS لعشرات
الجداول. أي تخصيص مستقبلي للمكاتب يُبنى كطبقة إضافية فوقها لا بديلاً عنها.

| الدور | الوصف التشغيلي |
|---|---|
| `owner` | مالك المكتب. الوحيد الذي يتجاوز العلامة المائية ويملك بيانات المكتب. |
| `admin` | مدير المكتب: الفريق، الإعدادات، الاشتراك. |
| `lawyer` | محامٍ: القضايا والجلسات والمهل والمستندات. |
| `legal_assistant` | مساعد قانوني: إدخال ومتابعة دون عمليات حساسة. |
| `viewer` | اطلاع فقط. |

### 2.2 أدوار المنصة (Platform Roles) — غير محدودة

`platform_staff.role` يحمل قيمتين فقط: `super_admin` (يتجاوز كل تحقق) و`staff`.
الصلاحية الفعلية لموظف `staff` = **اتحاد**:

```
الصلاحيات الفعّالة = صلاحيات الدور (platform_roles.permissions)
                   ∪ الصلاحيات الفردية (platform_staff.permissions)
                   ∪ الصلاحيات المؤقتة السارية (المرحلة الثالثة)
                   ∪ الصلاحيات المفوَّضة السارية (المرحلة الثالثة)
```

`platform_roles` جدول حر: عدد الأدوار غير محدود، وكل دور يحمل مصفوفة صلاحيات.
`is_system = true` يحمي الأدوار التأسيسية من الحذف.

## 3) الصلاحيات: Resource + Action

كل صلاحية مفتاح نصي بالصيغة `resource.action` — مثال: `billing.issue`،
`staff.manage`، `audit.export`. المرجع الوحيد للمفاتيح:
`src/lib/admin-permissions.ts` (`AdminPermission` + `ADMIN_PERMISSIONS`).

المجموعات الحالية: المستخدمون، المكاتب، الإيرادات، الدعم الفني، التشغيل،
الأمان، الفريق، المركز المالي.

مجموعات المرحلة الثالثة (تُضاف كمفاتيح جديدة، دون إعادة تسمية القديم):

| المجموعة | أمثلة المفاتيح |
|---|---|
| الأقسام والموظفون | `departments.read` `departments.manage` `staff.evaluate` `staff.sessions.read` `staff.sessions.revoke` `staff.restrictions.manage` |
| التفويض والاعتماد | `delegation.grant` `delegation.revoke` `approvals.request` `approvals.decide` |
| الانتحال | `impersonation.request` `impersonation.approve` |

قواعد إلزامية للمفاتيح:
1. المفتاح يُضاف في `admin-permissions.ts` أولاً — لا مفاتيح سحرية في الكود.
2. لكل مفتاح `label` و`group` و`description` عربي واضح.
3. لا تُحذف مفاتيح قديمة؛ تُترجم عبر `LEGACY_ALIASES` (`expandPermissions`).
4. أي مفتاح غير معرّف = **مرفوض** (Default Deny).

### 3.1 الصلاحيات المؤقتة (Time-boxed Permissions)

منح صلاحية لموظف بمدة `starts_at → expires_at` وسبب إلزامي. تُحسب ضمن
الصلاحيات الفعّالة فقط أثناء نافذتها الزمنية، وتنتهي تلقائياً بمرور الوقت
(لا تعتمد على مهمة تنظيف: التحقق زمني عند كل طلب). كل منح وكل سحب في سجل التدقيق.

### 3.2 تفويض الصلاحيات (Delegation)

موظف يفوّض جزءاً من صلاحياته لموظف آخر (إجازة، انتداب) بشرطين لا يقبلان التجاوز:
- **لا تصعيد**: لا يُفوَّض إلا ما يملكه المفوِّض فعلاً وقت التفويض.
- **لا تفويض متسلسل**: الصلاحية المفوَّضة لا تُفوَّض مرة أخرى.

التفويض دائماً مؤقت (له `expires_at`)، وقابل للسحب فوراً، ويُسجَّل باسم
المفوِّض والمفوَّض إليه معاً في كل عملية تُنفَّذ عبره.

### 3.3 Approval Workflow

العمليات عالية الخطورة لا تُنفَّذ بقرار موظف واحد. النمط الموحد:

```
طلب (requested_by, reason)
   → مراجعة موظف آخر يملك صلاحية القرار (approvals.decide)
   → approved / rejected  → تنفيذ بعد الاعتماد فقط
```

قواعد ثابتة:
- **Four-Eyes**: `approved_by ≠ requested_by` (يُفرض في قاعدة البيانات لا في الواجهة).
- كل طلب له `expires_at`؛ الطلب المنتهي لا يُنفَّذ.
- السبب إلزامي في الطلب وفي القرار.
- العمليات الخاضعة للاعتماد: إعادة فتح فترة مالية (قائم فعلاً:
  `platform_period_reopen_approvals`)، حذف مكتب أو مستخدم، منح
  `super_admin`، الانتحال، منح صلاحية مؤقتة حساسة، تصدير سجل التدقيق.

## 4) العلاقات بين الأقسام (Departments)

```text
platform_departments
    ├── code / name_ar / manager_user_id (مدير القسم)
    └── parent_department_id  ← شجرة أقسام (قسم رئيسي وفروعه)

platform_staff
    ├── department_id      ← القسم
    ├── manager_user_id    ← المدير المباشر
    └── role_id            ← دور المنصة
```

قواعد العلاقة:
- القسم يحمل **دوراً افتراضياً** يُطبَّق على الموظف الجديد فيه.
- المدير المباشر هو الوجهة الطبيعية لطلبات الاعتماد الخاصة بموظفيه.
- شجرة الأقسام تمنع الحلقات (لا يكون القسم أباً لنفسه ولا لسلفه).
- القسم **ليس** حدود صلاحية بذاته؛ الصلاحية تبقى من الدور/الفرد. القسم تنظيمي
  وتوجيهي (Routing) للتذاكر والاعتمادات والتقارير.

الربط مع الأقسام الوظيفية اللاحقة: الدعم الفني، البريد الداخلي، المهام
الداخلية، عروض الأسعار، العقود — كلها تُوجَّه بالقسم وتُصرَّح بالصلاحية.

## 5) صلاحيات موظفي مِهلة

- `super_admin`: يتجاوز كل تحقق صلاحية (لا يتجاوز حظر الاطلاع على بيانات المكاتب).
- `staff`: لا يملك شيئاً افتراضياً — Default Deny مطلق.
- التحقق الفعلي على الخادم فقط عبر `requireStaff(supabase, userId, permission)`
  في `src/lib/admin-guard.server.ts`. الواجهة (`usePlatformAdmin().can`) للإخفاء
  البصري فقط ولا تُعتبر حماية.
- الموظف `suspended` = لا وصول، مهما كانت أدواره.

## 6) صلاحيات عملاء المنصة (المكاتب)

- الوصول محدد بـ `organization_members` بحالة `active` فقط.
- RLS على كل جدول بيانات يقيّد الصفوف بمكتب المستخدم — العزل في قاعدة البيانات
  لا في الكود.
- الصلاحيات الوظيفية داخل المكتب من مصفوفة الدور (`doc-permissions.ts`)،
  وتُفرض على الخادم عبر `requireSensitiveAccess`
  (`src/lib/security/sensitive-guard.server.ts`).
- عضوية `pending` → صفحة `/pending-access`؛ بلا عضوية → `/onboarding`.

## 7) آلية التفويض (Authorization Flow)

مسار كل عملية إدارية، دون استثناء:

```text
المتصفح
  → serverFn (createServerFn)
  → requireSupabaseAuth   (تحقق الرمز الموقّع → userId + claims)
  → requireStaff(permission)  (الدور + الفرد + المؤقت + المفوَّض)
  → قيود الجلسة (IP / الجهاز / نافذة العمل)
  → اعتماد مطلوب؟ → مسار Approval
  → تنفيذ العملية
  → writeAudit(before/after + IP + الجهاز + معرّف التتبع)
```

مبادئ:
1. **لا تحقق في العميل**: كل قرار وصول يُتخذ على الخادم.
2. **Default Deny**.
3. **قرار واحد لكل عملية**: لا تحقق مزدوج متناقض.
4. **رسائل عربية مهنية** عند الرفض، دون كشف تفاصيل تقنية.

## 8) الانتحال (Impersonation)

الانتحال مسموح **داخل نطاق المنصة فقط** ولا يُستخدم أبداً للاطلاع على بيانات
مكتب. الاطلاع على بيانات المكاتب يبقى محصوراً بـ `support_access_grants`.

القواعد:
- يتطلب `impersonation.request` + اعتماد موظف آخر (`impersonation.approve`).
- سبب إلزامي، ومدة قصوى صريحة، وانتهاء تلقائي.
- **قراءة فقط**: أي عملية كتابة أثناء الانتحال مرفوضة على الخادم.
- كل عملية أثناء الانتحال تُسجَّل بالفاعل الحقيقي **و**الشخصية المنتحلة معاً.
- شريط تحذير دائم في الواجهة أثناء الجلسة، وإمكانية إنهاء فوري.
- سجل مستقل لكل جلسة انتحال (بدء/انتهاء/من أنهاها).

---

## 9) أمان الجلسة (Session Security)

- الجلسة من Supabase Auth؛ الرمز الموقّع يُرفق بكل نداء خادم عبر
  `functionMiddleware` (`src/start.ts`).
- التحقق بخطوتين (MFA/TOTP) **اختياري** للمستخدمين، ومستوى التحقق (`aal1/aal2`)
  يُقرأ من الرمز ويُسجَّل في سجل التدقيق (`assuranceLevel`).
- سجل جلسات موظفي المنصة: الجهاز، المتصفح، نظام التشغيل، IP، آخر نشاط،
  مع **إبطال فوري** لأي جلسة (`staff.sessions.revoke`).
- القيود لكل موظف: قائمة IP مسموحة (CIDR)، أجهزة موثوقة، نافذة زمنية للعمل
  بتوقيت الرياض. القيد يُفحص على الخادم في كل عملية، لا عند الدخول فقط.
- تجاوز القيد لا يُسجَّل كخطأ صامت: يُرفض ويُكتب في سجل التدقيق.

## 10) استراتيجية التدقيق (Audit Strategy)

| السجل | المحتوى |
|---|---|
| `admin_audit_logs` | كل عملية إدارية: الفاعل، الحدث، قبل/بعد، IP، الجهاز |
| `activity_logs` | نشاط المكاتب (يخصّ التينانت) |
| `pii_access_logs` | كل كشف لبيانات هوية |
| `print_audit_logs` | كل طباعة/تصدير |
| `document_access_logs` | كل وصول لمستند |
| `system_failures` | الأعطال بمعرّف `MF-XXXXX` |

قواعد:
- **الفاعل تُثبّته قاعدة البيانات** عبر مُشغّلات (`admin_audit_enforce_actor`) —
  لا يمكن انتحاله من العميل.
- السجلات **غير قابلة للتعديل أو الحذف** (لا `UPDATE`/`DELETE`).
- كل عملية حساسة تحمل **معرّف تتبع** (`newTraceRef`) يربط الطلب بالسجل.
- كل تعديل على أي عنصر RBAC (دور، صلاحية، تفويض، منح مؤقت، قيد، اعتماد،
  انتحال، جلسة) يكتب سجلاً بقيمة قبل وبعد — بلا استثناء.

## 11) القيود في قاعدة البيانات (Invariants)

1. RLS مفعّل على كل جدول، مع `GRANT` صريح لكل جدول عام.
2. جداول RBAC للمنصة: لا وصول لـ `anon`؛ الكتابة عبر دوال الخادم فقط.
3. `approved_by ≠ requested_by` على كل جدول اعتماد.
4. الصلاحية المؤقتة/المفوَّضة تتطلب `expires_at > starts_at`، والتحقق زمني.
5. لا يُحذف آخر `super_admin` نشط.
6. لا حلقات في شجرة الأقسام ولا في سلسلة المدير المباشر.
7. القيود الزمنية تُفحص بمُشغّلات (Triggers) لا بـ `CHECK` (عدم ثبات `now()`).

## 12) قرارات معمارية

| القرار | السبب |
|---|---|
| أدوار المكتب ثابتة، أدوار المنصة حرّة | تغيير أدوار المكتب يلمس RLS لعشرات الجداول؛ خطر لا يقابله عائد. |
| الصلاحية = اتحاد (دور + فرد + مؤقت + مفوَّض) | مرونة تشغيلية دون تفتيت الأدوار. |
| Default Deny | خطأ الإضافة أرخص من خطأ التسريب. |
| الانتحال قراءة فقط، وخارج بيانات المكاتب | يحفظ سرية العميل القانوني ومسؤولية المنصة. |
| التحقق بخطوتين اختياري | قرار تجاري معتمد سابقاً؛ يُسجَّل ولا يُفرض. |
| Four-Eyes في القاعدة لا الواجهة | الواجهة قابلة للتجاوز، القاعدة لا. |
| المفاتيح لا تُحذف بل تُترجم | يمنع فقدان صلاحيات موظفين قائمين عند التطوير. |
| المركز المالي مجمَّد | استقرار مالي مُختبَر؛ التعديل بسبب مؤكَّد فقط. |

---

## 13) ترتيب التنفيذ

1. **RBAC** (هذه الوثيقة): الصلاحيات الدقيقة، المؤقتة، التفويض، الاعتماد،
   الانتحال، سجل التدقيق، الفرض الخادمي الكامل + اختبار عملي.
2. **الموظفون والأقسام**: الأقسام، المدير المباشر، الدعوات، الحالات، التقييم،
   سجل النشاط، الجلسات والأجهزة، قيود IP/الجهاز/الوقت.
3. **بعد اكتمال (1) و(2) واختبارهما**: البريد الداخلي، الدعم الفني، المهام
   الداخلية، عروض الأسعار للشركات، العقود.

لا تبدأ مرحلة قبل اكتمال ما قبلها واختباره عملياً.
