# تكامل Hostinger Agentic Mail — مِهلة

وثيقة معمارية وتشغيلية لتكامل بريد Hostinger عبر بروتوكول MCP داخل Email Workspace،
ومصدر الحقيقة لأي تعديل لاحق على هذا المسار.

## 1. النطاق والمبدأ

- التكامل **قناة إضافية** ضمن طبقة مزوّدين محايدة، ولا يستبدل مسار SMTP/IMAP القائم.
- لا حالة تجميلية: «متصل» و«مُفعّل» و«مدعوم» لا تُمنح إلا بنتيجة نداء حقيقي من الخادم.
- Fail-Closed: أي شرط غير مستوفى يمنع التفعيل، وأي أداة غير مكتشفة تعني عملية غير مدعومة.
- المفتاح `HOSTINGER_MAIL_API_TOKEN` سرّ خادمي فقط؛ لا يُعاد للواجهة ولا يُسجّل ولا يُخزّن في القاعدة.

## 2. الملفات

### نموذج الحساب الحقيقي والأسماء المستعارة

في إعداد Hostinger الحالي هناك **حساب حقيقي واحد** يملك بيانات الدخول
(`noreply@mehlalex.com`)، أما `support` و`sales` و`billing` و`legal` و`info`
فهي **أسماء مستعارة** تُسلَّم إلى الحساب الحقيقي:

- السحب يجري من الحساب الحقيقي فقط؛ حالة الأسماء المستعارة `alias` وليست خللاً.
- الصندوق المنطقي يُحدَّد من الترويسات: `Delivered-To` ← `X-Original-To` ← `To` ← `Cc`
  عبر `src/lib/email/routing.server.ts`.
- الاستيعاب تحت الحساب الحقيقي ممنوع: رسالة بلا اسم مستعار مطابق تُرفض (Fail-Closed).
- مسار IMAP يصادق فقط على العناوين التي تملك أسراراً خاصة بها.

## 4. الأمان

- **التصريح**: كل دالة تمر بـ `authorize` → `requireStaff` على صفّ الموظف في القاعدة.
- **النطاق**: الصناديق تُقيّد بـ `assertMailboxAccess` ونطاق قسم الموظف؛ لا يُقبل نطاق من الواجهة.
- **صندوق النظام**: `noreply` مستثنى من الإرسال والمزامنة البشرية.
- **التدقيق**: كل عملية تكتب في `email_audit_logs` مع `request_id` و`correlation_id` ووصف منقّح.
- **التنقيح**: `redactAgentic` + `toSafeFailure` يمنعان أي رمز أو ترويسة أو مسار من الظهور.
- **المهلة**: 45 ثانية لكل نداء مزوّد حتى لا تتجمّد الواجهة.
- **حواجز آلية**: `bun run security:check` يفشل عند كتابة الرمز في الكود أو قراءته خارج ملفات `*.server.ts`.

## 5. المزامنة التزايدية ومنع التكرار

- المؤشر لكل صندوق في `email_sync_state` (`provider = 'agentic_mail'`, `provider_cursor`).
- منع التكرار يعتمد على `message_id` الفعلي، لذا تصفير المؤشر لا يُنشئ رسائل مكرّرة.
- كل دورة تُسجَّل في `email_sync_runs`: مقروء/مستورد/مكرّر/تذاكر/مدّة/سبب الفشل.
- الرسائل الواردة تُربط بمركز الدعم عبر مسار الاستيعاب القائم (`ingest.server.ts`).

## 6. الجدولة وقاطع الدائرة

| العنصر | القيمة |
| --- | --- |
| الفاصل الطبيعي | 5 دقائق |
| التراجع عند الفشل | 60 ثانية × 2^(عدد الفشل) حتى 60 دقيقة |
| فتح القاطع | 5 حالات فشل متتالية → توقّف ساعة |
| الإيقاف التلقائي | 3 حالات فشل مصادقة → تعطيل التكامل + عطل في `system_failures` |
| منع التداخل | قفل جدولة (10 دقائق) + قفل صندوق داخل المحرّك |

الاستئناف بعد الإيقاف التلقائي: تدوير المفتاح ← اختبار الاتصال ← «إعادة المحاولة» ← «تفعيل».

## 7. مسار الإرسال

- إن كانت أداة الإرسال مكتشفة: الإرسال يمر بالمزوّد، وأي فشل غير مدعوم يعود إلى SMTP القائم.
- إن لم تُكتشف: الإرسال يبقى SMTP بالكامل، وشرط «رسالة الاختبار» يُعتبر غير مطلوب.

## 8. شروط التفعيل

1. المفتاح مُعرّف في أسرار المنصة.
2. اختبار اتصال ناجح.
3. أدوات تغطي قراءة الرسائل.
4. صندوق واحد مرتبط على الأقل.
5. تشغيل تجريبي ناجح.
6. رسالة اختبار ناجحة — عند دعم الإرسال فقط.
