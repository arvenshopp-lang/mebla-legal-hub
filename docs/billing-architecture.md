# معمارية المركز المالي — منصة مِهلة

وثيقة مرجعية للمركز المالي في لوحة `/mehla-admin/billing`. تصف البنية الفعلية
المطبَّقة في الكود وقاعدة البيانات، لا التصميم المقترح.

- آخر تحديث: 2026-08-04
- النطاق: فوترة **المنصة للمكاتب** (اشتراكات مِهلة)، وليس فوترة المكاتب لعملائها.
- العملة الأساسية: `SAR`. المنطقة الزمنية المرجعية للترقيم والتقارير: `Asia/Riyadh`.

---

## 1. مخطط الجداول والعلاقات

```text
organizations ─┬─< platform_invoices ─┬─< platform_invoice_items
               │                      ├─< platform_payments ──< platform_refunds
               │                      ├─< platform_credit_notes
               │                      ├─< platform_payment_attempts
               │                      └─< platform_payment_webhooks
               └─< subscriptions

platform_integrations ──< platform_payment_provider_configs
platform_bank_reconciliations >── platform_payments   (مطابقة يدوية)
platform_financial_periods ──< platform_period_reopen_approvals
platform_number_sequences   (مستقل — مصدر الترقيم)
platform_billing_notes      (ملاحظات إدارية على السجلات المالية)
admin_audit_logs            (سجل تدقيق كل عملية مالية)
```

| الجدول | الدور |
| --- | --- |
| `platform_invoices` | رأس الفاتورة: الرقم، الحالة، الإجماليات، الضريبة، الاستحقاق، بيانات المشتري المجمّدة عند الإصدار. |
| `platform_invoice_items` | بنود الفاتورة (الوصف، الكمية، السعر، الخصم، الضريبة، الإجمالي). |
| `platform_payments` | الدفعات المرتبطة بفاتورة: المبلغ، الطريقة، المزوّد، المرجع، الحالة، معتمِد الدفعة. |
| `platform_refunds` | استردادات مرتبطة بدفعة محددة (لا يوجد استرداد بلا دفعة أصل). |
| `platform_credit_notes` | إشعارات دائنة على فاتورة صادرة (بديل التعديل الممنوع). |
| `platform_payment_attempts` | محاولات إنشاء/تحقق عبر المزوّد مع `correlation_id` و`request_id`. |
| `platform_payment_webhooks` | كل حدث وارد من مزوّد الدفع مع حالته وعدد المحاولات وحمولته المُقنَّعة. |
| `platform_payment_provider_configs` | إعدادات المزوّد لكل وضع تشغيل (تجريبي/إنتاج) وحالة التفعيل. |
| `platform_integrations` + `integration_secrets` | تخزين مفاتيح المزوّد مشفّرة (AES-256-GCM) خارج جداول الفوترة. |
| `platform_number_sequences` | عدّادات الترقيم لكل نوع مستند ولكل سنة. |
| `platform_financial_periods` | الفترات المالية وحالة الإقفال. |
| `platform_period_reopen_approvals` | طلبات إعادة فتح فترة مقفلة واعتمادها (مبدأ أربع أعين). |
| `platform_bank_reconciliations` | حركات كشف الحساب البنكي وربطها بالدفعات. |

كل الجداول أعلاه مفعّل عليها RLS، وسياساتها تسمح لموظفي المنصة فقط (`platform_staff`)
وفق الصلاحية المطلوبة؛ لا يملك المستخدم النهائي (`authenticated` عادي) أي وصول مباشر.

## 2. دورة حياة الفاتورة (State Machine)

الحالات المعرّفة في `src/lib/billing/billing.shared.ts`:
`draft, issued, pending, paid, partially_paid, overdue, cancelled, refunded, partially_refunded`.

```text
            ┌──────────┐  تعديل/حذف مسموح
            │  draft   │
            └────┬─────┘
       إصدار (billing.issue) — يمنح رقماً نظامياً ويجمّد المحتوى
            ┌────▼─────┐
            │  issued  │──── إلغاء (بلا دفعات) ──► cancelled
            └────┬─────┘
     أول دفعة مُعتمدة جزئية│         │ مرور تاريخ الاستحقاق بلا سداد
            ┌────▼──────────┐   ┌────▼─────┐
            │ partially_paid│   │ overdue  │
            └────┬──────────┘   └────┬─────┘
       اكتمال السداد│                 │ سداد كامل
            ┌──────▼─────┐            │
            │    paid    │◄───────────┘
            └──────┬─────┘
     استرداد جزئي  │  استرداد كامل
   partially_refunded ◄─┴─► refunded
```

قواعد ثابتة:

- **قبل الإصدار**: التعديل والحذف مسموحان فقط في `draft`.
- **بعد الإصدار**: الفاتورة غير قابلة للتعديل نهائياً؛ التصحيح يتم بإشعار دائن
  (`platform_credit_notes`) أو بالإلغاء إن لم تُسجَّل أي دفعة.
- **لا رجوع للخلف**: حارس `invoice_immutability_guard` يمنع إعادة أي فاتورة صادرة
  إلى `draft`.
- **حالة السداد محسوبة**: `partially_paid / paid` تُشتق من مجموع الدفعات المعتمدة
  مقابل الإجمالي، ولا تُكتب يدوياً من الواجهة.
- **الفترات المقفلة**: أي عملية تؤثر على فترة مقفلة تُرفض على مستوى قاعدة البيانات.

## 3. دورة حياة الدفع

الحالات: `pending, processing, paid, failed, cancelled, refunded, partially_refunded`.

```text
تسجيل يدوي (billing.record_payment)   إنشاء عبر مزوّد (createPayment)
            │                                     │
            ▼                                     ▼
        pending ────► اعتماد إداري ──► paid    processing ──webhook──► paid / failed
            │  (billing.approve_payment)
            └────► رفض ──► cancelled / failed
```

- **الفصل بين التسجيل والاعتماد**: صلاحية `billing.record_payment` تُسجّل الدفعة
  فقط، و`billing.approve_payment` تعتمدها. لا تُحدَّث حالة الفاتورة إلا عند الاعتماد.
- **المسار الآلي**: دفعات المزوّد لا تُعتمد يدوياً؛ الويبهوك (أو `getPaymentStatus`)
  هو مصدر الحقيقة.
- **كل محاولة موثّقة**: تُكتب في `platform_payment_attempts` مع `correlation_id`
  و`request_id` لتتبع العملية من الواجهة حتى المزوّد.
- **حد أعلى صارم**: دالة حماية في قاعدة البيانات تمنع تجاوز مجموع الدفعات المعتمدة
  لإجمالي الفاتورة، مع قفل صف الفاتورة (`FOR UPDATE`) لمنع تعارض العمليات المتزامنة.

## 4. دورة حياة الاسترداد

```text
طلب استرداد (billing.refund) ──► pending
        │ اعتماد                         │ رفض
        ▼                                ▼
   processing ──► completed          rejected
        └── فشل عند المزوّد ──► failed
```

- الاسترداد مرتبط دائماً بدفعة `paid` واحدة، وليس بالفاتورة مباشرة.
- دالة حماية تمنع تجاوز مجموع الاستردادات للمبلغ المسدَّد فعلياً على تلك الدفعة.
- عند اكتمال الاسترداد تُحدَّث حالة الدفعة (`refunded` / `partially_refunded`)
  ثم حالة الفاتورة تبعاً لذلك.
- الاسترداد اليدوي (تحويل بنكي عكسي) يُغلق إدارياً مع سبب مُسجَّل في سجل التدقيق؛
  استرداد المزوّد يمر عبر `refundPayment` ثم يُؤكَّد بالويبهوك.
- الاسترداد داخل فترة مالية مقفلة مرفوض؛ البديل إشعار دائن في الفترة المفتوحة.

## 5. دورة حياة Webhook

نقطة الاستقبال: `src/routes/api/public/payments/$provider.ts` → `handleProviderWebhook`
في `src/lib/billing/webhooks.server.ts`.

```text
POST /api/public/payments/{provider}
   1) قراءة الجسم الخام كنص (لا JSON قبل التحقق)
   2) التحقق من التوقيع عبر validateWebhookSignature للمزوّد  ── فشل ► 401 + تسجيل rejected
   3) تسجيل الحدث في platform_payment_webhooks (حمولة مُقنَّعة عبر maskSensitive)
   4) منع الازدواجية: (provider_code, event_id) فريد ► duplicate ويُعاد 200
   5) المعالجة: مطابقة provider_payment_id ► تحديث الدفعة ► تحديث الفاتورة
   6) النتيجة: processed | failed (تُعاد للطابور) | dead_letter
```

- **دائماً 200 عند النجاح أو التكرار** حتى لا يعيد المزوّد الإرسال بلا داعٍ.
- **إعادة المحاولة**: `processRetryQueue` بتراجع تصاعدي، وبعد استنفاد المحاولات
  ينتقل الحدث إلى `dead_letter` ويظهر في لوحة الويبهوك لإعادة الفتح اليدوي
  (`reopenWebhookEvent`) بسبب مُسجَّل.
- **لا أسرار في السجلات**: `maskSensitive` تُقنّع المفاتيح والتوكنات قبل التخزين.
- **حماية SSRF/الحقن**: لا يُنفَّذ أي فعل مالي إلا بعد مطابقة الحدث بدفعة قائمة
  في قاعدة البيانات؛ حمولة المزوّد لا تنشئ فواتير أو مبالغ من العدم.

## 6. الصلاحيات المالية

تُعرَّف في `src/lib/admin-permissions.ts` وتُفرض خادمياً في `billingCtx` عبر
`requireStaff(supabase, userId, permission)` — لا تعتمد الواجهة أبداً كمصدر تفويض.

| الصلاحية | تسمح بـ |
| --- | --- |
| `billing.read` | الاطلاع على الفواتير والدفعات والاستردادات. |
| `billing.create` / `billing.update` | إنشاء وتعديل المسودات وبنودها. |
| `billing.issue` | إصدار الفاتورة برقم نظامي نهائي. |
| `billing.cancel` | إلغاء فاتورة غير مسددة بسبب مُسجَّل. |
| `billing.record_payment` | تسجيل دفعة بانتظار الاعتماد. |
| `billing.approve_payment` | اعتماد الدفعة أو رفضها. |
| `billing.refund` | إنشاء الاستردادات والبت فيها. |
| `billing.reconcile` | إدخال حركات بنكية ومطابقتها. |
| `billing.close_period` / `billing.reopen_period` | إقفال الفترات واعتماد إعادة فتحها. |
| `billing.manage_providers` | إدارة مزوّدي الدفع ومفاتيحهم وأوضاع التشغيل. |
| `billing.view_reports` / `billing.export` | التقارير والتصدير وملفات PDF. |

مبادئ مطبَّقة: **فصل المهام** (المسجِّل ≠ المعتمِد)، **أربع أعين** لإعادة فتح
الفترات، و**سجل تدقيق إلزامي** (`admin_audit_logs`) لكل عملية كتابة مالية.

## 7. القيود الموجودة في قاعدة البيانات

هذه القيود هي خط الدفاع الأخير، ومستقلة عن الواجهة وعن دوال الخادم:

- **قيود `CHECK` على الفواتير**: منع المتبقي السالب، ومنع تجاوز الخصم للمجموع
  الفرعي، وضمان عدم سلبية المبالغ والنسب.
- **فهرس فريد جزئي** على مرجع المزوّد في الدفعات (يستثني المحاولات الفاشلة) لمنع
  ازدواج تسجيل الدفعة نفسها.
- **فريد على أحداث الويبهوك** `(provider_code, event_id)` لضمان Idempotency.
- **فريد على رقم المستند** لكل نوع مستند.
- **دوال حماية `SECURITY DEFINER` + Triggers**:
  - منع تجاوز مجموع الدفعات لإجمالي الفاتورة.
  - منع تجاوز مجموع الاستردادات للمبلغ المسدَّد.
  - `invoice_immutability_guard`: منع تعديل الفواتير الصادرة وإرجاعها إلى مسودة.
  - رفض أي كتابة تقع داخل فترة مالية مقفلة.
  - `admin_audit_enforce_actor`: منع كتابة سجل تدقيق بمنفّذ منتحَل.
- **قفل الصفوف** (`SELECT ... FOR UPDATE`) داخل دوال الحماية لتفادي سباق العمليات
  المتزامنة.
- **فهارس أداء** على الحقول المالية الحساسة (المؤسسة، الحالة، تاريخ الإصدار
  والاستحقاق، مرجع المزوّد) لدعم التقارير والتقادم (Aging).

## 8. آلية الترقيم

الدالة: `public.next_financial_number(_kind)` — `SECURITY DEFINER`، على جدول
`platform_number_sequences`.

- الأنواع المدعومة: `invoice`, `quote`, `credit_note`.
- الصيغة: `PREFIX-YYYY-NNNNNN` مثل `MEH-INV-2026-000001`.
- البادئات الافتراضية: `MEH-INV`, `MEH-QT`, `MEH-CN` — قابلة للتعديل من إعدادات
  الترقيم في اللوحة (مع معاينة عبر `billingPreviewSequence`).
- **السنة** تُحسب بتوقيت `Asia/Riyadh`، والعدّاد يُصفَّر مع بداية كل سنة.
- **منع التكرار تحت التزامن**: `pg_advisory_xact_lock` على مفتاح `kind:period`
  قبل زيادة العدّاد، إضافة إلى القيد الفريد على الرقم الناتج.
- الرقم يُمنح **عند الإصدار فقط**، لا عند إنشاء المسودة، فلا توجد فجوات ترقيم
  ناتجة عن مسودات مهملة.

## 9. آلية PDF

الملفات: `src/lib/billing/pdf/engine.server.ts` (المحرك) و`models.server.ts`
(نماذج المستندات)، والتنزيل من الواجهة عبر `src/lib/billing/download-pdf.ts`.

- **أربعة مستندات موحّدة**: الفاتورة الضريبية، عرض السعر، إيصال السداد، كشف الحساب.
- **المكتبات**: `pdf-lib` + `@pdf-lib/fontkit` مع خط عربي مضمّن؛ التشكيل عبر
  `arabic-shaper` الداخلي.
- **معالجة الاتجاه (BiDi)**: يقسّم المحرك كل سطر إلى «مقاطع اتجاهية»
  (`splitDirectionalRuns`): العربية RTL، والأرقام واللاتينية LTR، والمحايدات تلتحق
  بالمقطع المجاور. ثم تُرسم المقاطع بمواضع محسوبة من اليمين لليسار. هذا يمنع
  انقلاب التواريخ والمبالغ وأرقام الجوال.
- **قواعد خاصة**: البادئات (`+`, `#`) تبقى مع الرقم، واللواحق (`%`) كذلك، ووحدة
  «المبلغ + رمز العملة» غير قابلة للكسر عند الالتفاف أو القصّ (`tokenize`).
- **تعدد الصفحات**: تقسيم تلقائي مع ترويسة وتذييل موحدين وترقيم «صفحة س / ص».
- **التسليم**: تُرجع دوال الخادم (`billingInvoicePdf` وأخواتها) الملف مُرمَّزاً
  Base64 مع اسم الملف، وتُنزَّل في المتصفح بنوع `application/pdf`.
- **الأرقام دائماً لاتينية** داخل المستندات المالية لضمان قابلية القراءة الآلية
  والتدقيق.

## 10. إضافة مزوّد دفع جديد

المزوّدون خلف واجهة واحدة في `src/lib/billing/providers.server.ts`:

```ts
export interface PaymentProvider {
  readonly code: ProviderCode;
  readonly requiresCredentials: boolean;
  readonly requiredCredentialKeys: string[];
  createPayment(input, creds): Promise<ProviderPaymentState>;
  verifyPayment(providerPaymentId, creds): Promise<ProviderPaymentState>;
  getPaymentStatus(providerPaymentId, creds): Promise<ProviderPaymentState>;
  refundPayment(providerPaymentId, amount, creds): Promise<{ providerRefundId; status; raw }>;
  validateWebhookSignature({ rawBody, headers, creds }): boolean;
  handleWebhook(rawBody): WebhookEvent;
  testConnection(creds): Promise<{ ok: boolean; message: string }>;
}
```

الخطوات:

1. أضف الرمز إلى `ProviderCode` ونفّذ كائناً يحقق `PaymentProvider`.
2. سجّله في خريطة `PROVIDERS` — لا حاجة لتعديل أي منطق فوترة آخر.
3. عرّف مفاتيحه في `requiredCredentialKeys`؛ تُحفظ مشفّرة في `integration_secrets`.
4. عرّف حالة المزوّد في `platform_payment_provider_configs` (وضع تجريبي/إنتاج).
5. الويبهوك يعمل تلقائياً على `/api/public/payments/{code}`.
6. **لا يُفعَّل المزوّد إلا بعد نجاح `testConnection` فعلياً** — هذه قاعدة مفروضة
   في محرك التفعيل وليست إجراءً اختيارياً.
7. حوّل حالات المزوّد إلى حالات المنصة داخل المُهيّئ نفسه؛ لا تُسرّب مفردات المزوّد
   إلى بقية النظام.

## 11. ربط مُيسّر (Moyasar) لاحقاً

التنفيذ جاهز بالكامل في `moyasarProvider` وينتظر المفاتيح والتفعيل فقط:

1. من `/mehla-admin/billing` → المزوّدون: أدخل `secret_key` و`webhook_secret`
   لوضع **التجريب** أولاً.
2. اضغط «اختبار الاتصال» — يستدعي `GET /payments?per=1` فعلياً؛ التفعيل مرفوض
   ما لم ينجح.
3. اضبط عنوان الويبهوك عند مُيسّر على:
   `https://mehlalex.com/api/public/payments/moyasar`
   (أو نطاق المعاينة عند الاختبار).
4. جرّب دفعة تجريبية: `createPayment` ينشئ فاتورة مُيسّر بالهللات
   (`amount × 100`) ويعيد `redirectUrl`، ثم يصل الحدث ويُحدِّث الدفعة والفاتورة.
5. بعد نجاح الاختبار، أدخل مفاتيح الإنتاج في وضع **الإنتاج** وفعّله.

ملاحظات تنفيذية مهمة:

- التحقق من التوقيع يدعم مسارين: ترويسة `x-moyasar-signature` بـ HMAC-SHA256 على
  الجسم الخام، أو `secret_token` داخل الحمولة — والمقارنة `timingSafeEqual`.
- كل المبالغ تُحوَّل من/إلى الهللات عند حدود المزوّد فقط.
- الاسترداد يمر عبر `POST /payments/{id}/refund` ثم يُؤكَّد بالويبهوك.

## 12. الافتراضات والقرارات المعمارية

1. **Payment-Provider-Agnostic**: قلب النظام لا يعرف أي مزوّد؛ كل خصوصية مزوّد
   محصورة في `providers.server.ts`. التحصيل اليدوي مزوّد كامل مثل غيره.
2. **الفاتورة الصادرة سجل نظامي لا يُعدَّل**: التصحيح بإشعار دائن أو إلغاء، احتراماً
   لمتطلبات الفوترة الضريبية السعودية.
3. **قاعدة البيانات هي المرجع الأمني**: القيود والحوارس تمنع الحالات المستحيلة حتى
   لو أخطأت الواجهة أو دالة الخادم.
4. **فصل التسجيل عن الاعتماد** في الدفعات والاستردادات، مع سجل تدقيق لا يمكن
   انتحال منفّذه.
5. **Idempotency أولاً**: كل حدث خارجي يحمل مفتاح تفرد؛ إعادة الإرسال لا تُنتج
   أثراً مالياً مضاعفاً.
6. **تخزين الأسرار خارج جداول الفوترة**، مشفّرة AES-256-GCM في مركز التكاملات،
   ولا تُسجَّل أبداً في الحمولات أو السجلات.
7. **الأرقام اللاتينية في المستندات المالية**، مع نصوص عربية RTL — قرار مقصود
   لضمان دقة القراءة والتدقيق والمطابقة البنكية.
8. **الترقيم عند الإصدار لا عند الإنشاء**، وتصفير سنوي بتوقيت الرياض.
9. **الفترات المالية تُقفل ولا تُفتح فردياً**: إعادة الفتح تحتاج طلباً واعتماداً من
   شخص آخر.
10. **رسائل الأخطاء عربية ومُهذَّبة**: `safeMessage` تمنع تسريب أي تفاصيل داخلية أو
    Stack Trace إلى الواجهة.
11. **العملة الحالية `SAR` فقط**: البنية تدعم حقل العملة، لكن لم تُختبر سيناريوهات
    متعددة العملات ولا أسعار الصرف.
12. **الخادم يعمل على بيئة Worker**: كل توليد PDF ومعالجة ويبهوك تعتمد مكتبات
    متوافقة مع Edge دون أي عمليات نظام تشغيل أو ملفات مؤقتة.

## 13. سياسة التغيير

المركز المالي مُغلق للتعديل. لا يُعدَّل أي جزء منه إلا عند:

- خلل مؤكَّد بدليل (سجل، بيانات، أو حالة قابلة لإعادة الإنتاج)، أو
- متطلب عمل جديد معتمَد.

وأي تغيير يشمل: تحديث هذه الوثيقة، وهجرة قاعدة بيانات عند الحاجة، وتأكيد بقاء
القيود والحوارس المذكورة في القسم 7 فعّالة.
