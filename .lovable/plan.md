## أعطال مفتوحة مثبتة بالدليل — أولوية 1 (Critical/High)

### 1. محرك الإشعارات نصف مبني — الأحداث لا تُعالج إطلاقاً
- الفجوة: `src/lib/notifications/` يحتوي `notifications.shared.ts` و`engine.server.ts` و`whatsline.server.ts` فقط. لا مشغّل طابور، لا مسار دوري، لا server functions، لا واجهة إدارية (البحث لم يجد أي مرجع لـ`notification_queue` خارج الأنواع والمحرك).
- الدليل من قاعدة البيانات: `notification_events = 8` كلها `processed_at IS NULL`، `notification_queue = 0`، `notification_rules = 0`.
- السبب الجذري: الجولة السابقة أنجزت الطبقة المشتركة والمزوّد وتوقفت قبل الطابور والتشغيل.
- الإصلاح: `queue.server.ts` (claim/backoff/idempotency عبر `claim_notification_batch` الموجودة) + مسار `api/public/hooks/notifications-dispatch` بنفس نمط `email-dispatch` المُثبت + قواعد افتراضية + لوحة مراقبة الطابور داخل `/mehla-admin/notifications`.
- Reuse: `claim_notification_batch`، `notification_attempts`، نمط `email-dispatch`، `integrationFetch`.
- الاختبار المغلق: حدث قضية حقيقي → قاعدة → مستلم → طابور → محاولة → تدقيق، مع مزوّد `not_configured` ينتج `WAITING FOR PROVIDER` لا فشل نظام.
- Regression: Triggers القضايا، لوحة الإدارة.
- Internal. لا يحتاج تدخلاً منك. ربط رقم WhatsApp الرسمي = External، خارج نطاق هذه الخطة.

### 2. رسائل بريد عالقة في الطابور منذ ثلاثة أيام
- الدليل: `email_outbox` = 10 sent / 8 failed / **4 queued أقدمها 2026-08-05 23:49** — أي لا Reaper ولا حد أقصى لعمر الرسالة.
- الإصلاح: تصنيف الرسائل العالقة، حد أقصى للعمر → `dead_letter` قابل للاسترجاع، وعرض العالق في `/mehla-admin/email` مع إجراء إعادة محاولة فعلي.
- الاختبار: رسالة عالقة مصطنعة تُصنّف وتظهر وتُعاد يدوياً بنجاح.

### 3. تصنيف `recipient_suppressed` كعطل نظام
- الدليل: `system_failures` = 34، منها **18 بـ`error_code = recipient_suppressed`** و15 بلا `error_code`.
- السبب: الحجب سلوك متوقع لا عطل، و`error_code` فارغ يمنع الفرز.
- الإصلاح: فصل الحجب إلى حالة بريد لا عطل، وإلزام `error_code` عند التسجيل.
- الاختبار: إرسال لعنوان محجوب → تنبيه عربي واضح في الواجهة، ولا صف جديد في `system_failures`.

### 4. عطل فعلي في خط معالجة المستندات (OCR)
- الدليل: `document_processing_jobs` = 3 completed / **3 failed** برسالة `undefined is not a function (near '...e of t...')` — خطأ JS داخل عامل المعالجة، ليس فشل مزوّد.
- الإصلاح: إعادة إنتاج الوظيفة الفاشلة على نفس الملف، تحديد الاستدعاء غير المتوافق مع بيئة الـWorker، إصلاحه، وإرجاع حالة فشل عربية مفهومة للمستخدم بدل رسالة تقنية.
- الاختبار: رفع PDF ممسوح → استخراج → فهرسة → بحث نصي ناجح، ثم ملف تالف → فشل آمن مفهوم.

### 5. تدقيق دوال الخادم غير المصادَقة
- الدليل: `client-portal.functions.ts` (4 دوال: `getUploadRequest`, `createUploadSlots`, `submitUploadRequest`, `lookupCaseStatus`) و`password-policy.functions.ts` بلا أي middleware — عامة بالتصميم.
- المطلوب: إثبات لكل واحدة: صلاحية الرمز ومدته، Rate limiting ومنع التعداد (`case_lookup_attempts` موجود — يجب إثبات إنفاذه)، وعدم تسريب أي بيانات مكتب أو عميل آخر أو ملاحظات داخلية.
- الاختبار: رمز صالح/منتهي/مزوّر/رمز مكتب آخر + قصف تعداد.

### 6. `organizationId` قادم من العميل في ~30 ملف دوال
- الدليل: البحث أظهر `organizationId: z.string().uuid()` في subscription، case-parties، secure-view، document-ai، pii، print-audit، invitations، documents/repair، admin-orgs وغيرها.
- المخاطرة: IDOR / cross-tenant إذا لم تُتحقق العضوية على الخادم بعد التحقق من التوكن.
- المطلوب: مصفوفة لكل دالة: هل تتحقق من عضوية `userId` في المؤسسة قبل أي قراءة/كتابة؟ ثم إصلاح الناقص فقط، مع مقارنة التغطية بمصفوفة RBAC الـ63 لتحديد ما لم يُغطَّ.
- Regression: `rbac:server:e2e` + `security:check` + `security:db`.

## أولوية 2 — إغلاق الرحلات والوحدات

### 7. الأزرار الميتة في لوحة المالك (36 مسار)
كل زر ونموذج وإجراء جدول وقائمة وحوار وتصدير وتفعيل/تعطيل واعتماد/رفض وحذف وإعادة محاولة واختبار اتصال وانتحال شخصية: يعمل فعلياً أو Disabled بسبب عربي حقيقي. تسجيل حكم لكل مسار. البداية بالمسارات الأثقل: settings (13 حالة disabled)، security (10)، seo (10)، email (5)، sms (5).

### 8. الرحلات الأساسية للمكتب كسلاسل
عميل → قضية → جلسة/مهلة/مهمة/مستند → إشعار → سجل تدقيق → أثر مرئي للعميل. لكل وحدة: إنشاء/قراءة/تعديل/حذف، بحث، فلترة، ترقيم، تحقق، صلاحيات، عزل، تدقيق، وحالات التحميل والفراغ والخطأ والنجاح. اختبار الفشل كما النجاح: غير مصرح، ممنوع، جلسة منتهية، إدخال خاطئ، إرسال مكرر، معرّف مكتب آخر، سجل محذوف، نقرة مزدوجة، تحديث أثناء العملية.

### 9. دورة حياة الحساب
تسجيل → تحقق بريد → دخول → Google → استعادة كلمة مرور → Onboarding → إنشاء مكتب → اشتراك → استحقاقات → خروج → انتهاء جلسة → مستخدم موقوف → عضو مُزال → دعوات. لا مصادقة جديدة، إثبات فقط.

### 10. الدعم والبريد
- الدعم: إنشاء → إسناد → دورة الحالة → ردود → ملاحظات داخلية → SLA → تصعيد → مرفقات → طابور بريد → CSAT → إغلاق/إعادة فتح. إثبات صريح: لا يمكن ربط تذكرة بمؤسسة أخرى عبر إدخال العميل، والملاحظة الداخلية لا تصل للعميل ولا للبريد.
- البريد: 6 صناديق و120 محادثة موجودة. الفصل الصريح بين INTERNAL TESTED و REAL SMTP/IMAP E2E، ومراجعة Send-As-Alias فعلياً لا من الواجهة.

### 11. الفوترة الداخلية والاشتراكات
`orgs = 23` وكلها لديها اشتراك (فحص الآن) — الثابت سليم. يبقى إثبات: الفواتير، المدفوعات، الاستردادات، الإشعارات الدائنة، الترقيم، الإجماليات وSAR بدون Float، قفل الفترات، انتقالات الحالة، Idempotency والويب هوك، المطابقة، الصلاحيات، وحدود الباقة على الخادم. المزوّد اليدوي/التجريبي يغلق المحرك الداخلي فقط ولا يُصنَّف External E2E.

### 12. المستندات والتخزين
22 مستنداً موجوداً. إثبات: خصوصية الـBucket، الروابط الموقعة قصيرة الصلاحية، العلامة المائية الخادمية، تحقق MIME وMagic Bytes والحجم، ملكية الملف والعزل، وفصل أحداث view/download/print/share في التدقيق دون خلط.

### 13. اللوحات والمؤشرات
لوحة المكتب ولوحة المالك: كل رقم من Backend حقيقي، Scope صحيح، فلاتر زمنية صحيحة، ولا مؤشر غير قابل للحساب يُعرض كرقم.
