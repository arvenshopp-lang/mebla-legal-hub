# MEHLA HARDENED HOSTILE-FILE SECURITY ARCHITECTURE — REVISION V3

معمارية ومراجعة تهديدات فقط. بلا Migration أو Schema أو Storage أو RLS أو Deploy أو Backfill أو Rescan أو نشر ماسح أو تعديل أسرار.

## 1. RESOLVED V2 CONTRADICTIONS

### 1.1 وصول الماسح إلى الحجر
العبارة الصحيحة ليست «الحجر لا يُصدر روابط موقّعة أبداً» بل:
- **NO_USER_ACCESSIBLE_QUARANTINE_URLS = TRUE** — لا رابط حجر يصل إلى متصفح أو عميل أو مكتب.
- **SCANNER_ONLY_READ_CAPABILITY** — قدرة قراءة واحدة، لكائن واحد، لهوية خدمة واحدة، لمدة واحدة.

| المعيار | 1: رابط موقّع خاص بالماسح | 2: وسيط بث خادمي مُصادق | 3: هوية خدمة تقرأ الكائن مباشرة | 4: **قدرة ذات نطاق واحد + بث من البوابة (المختار)** |
|---|---|---|---|---|
| الانكشاف | حامل الرابط يقرأ (Bearer) | لا رابط إطلاقاً | مفتاح خدمة دائم واسع | كائن واحد فقط، بلا رابط قابل لإعادة الاستخدام |
| الإبطال | متعذر قبل انتهاء المدة | فوري | يتطلب دوران المفتاح | فوري (إبطال قدرة في قاعدة البيانات) |
| قابلية التدقيق | إصدار الرابط فقط | كل بايت | ضعيفة | كل طلب قراءة مع scan_id |
| الأداء | ممتاز | جيد (قيود Worker) | ممتاز | جيد جداً |
| التعقيد | منخفض | متوسط | منخفض | متوسط |
| تسرّب الاعتماد | مرتفع | منخفض | مرتفع جداً | منخفض |
| إعادة الإرسال | ممكنة داخل المدة | ممنوعة | ممكنة | ممنوعة (استخدام واحد + nonce) |
| عزل المكاتب | بالمسار فقط | مُتحقَّق منه | ضعيف | مُتحقَّق منه لكل طلب |
| صلاحيات التخزين | قراءة على المخزن | لا شيء للماسح | قراءة واسعة | لا صلاحية تخزين للماسح إطلاقاً |

**المختار: الخيار 4.** بوابة الماسح تطلب من مِهلة «قدرة قراءة» مربوطة بـ `scan_id + object_key + sha256`، أحادية الاستخدام، عمرها 120 ثانية، وتُقدَّم عبر بث خادمي مُصادق بـ mTLS. الماسح **لا يملك أي صلاحية على Storage**، وكل قراءة تُدقَّق وتُبطَل فوراً بعد الاستخدام.

### 1.2 «الإبطال الفوري للروابط الموقّعة»
غير صحيح هندسياً: الرابط الموقّع الصادر لا يمكن سحبه قبل انتهائه. تُستبدل العبارة بـ: **SIGNED_URL_REVOCATION_GUARANTEED = NO** في التسليم المباشر، ولذلك يتغيّر نموذج التسليم (القسم 8).

### 1.3 وصول الملفات القديمة أثناء الترحيل
نافذة الثلاثين يوماً في V2 كانت Fail Open مقنّعاً. تُلغى ويحل محلها **Pre-Scan Before Enforcement** (القسم 11).

### 1.4 تحرير الملف الخبيث بموافقة مزدوجة
يُلغى نهائياً: **NORMAL_MALICIOUS_FILE_RELEASE_POSSIBLE = NO** (القسم 12).

### 1.5 تنزيل الأصل بعد CDR
يُقيَّد: التسليم الافتراضي مطهّر، والأصل يصبح وصولاً إثباتياً مقيّداً (القسم 15).

## 2. HOSTILE FILE PROCESSING ZONE
الماسح والمحللات و CDR تُعامل كمنطقة **يُفترض اختراقها**. كل ملف يُعامل كأنه قد ينفّذ شيفرة داخل المحلل.

**نموذج العزل الإلزامي لكل عامل فحص:**
حاوية غير مميزة · مستخدم غير جذري · نظام ملفات جذري للقراءة فقط · مساحة عمل مؤقتة على tmpfs بحجم محدود · إسقاط كل القدرات (`cap_drop: ALL`) · `no-new-privileges` · ملف تعريف seccomp مقيّد · AppArmor/SELinux · حدود CPU (1 vCPU) والذاكرة (512MB) والعمليات (`pids_limit=64`) وواصفات الملفات (1024) ومهلة تنفيذ صلبة (60 ثانية) · بلا Docker socket · بلا mounts من المضيف · بلا اعتمادات إنتاج مشتركة · مساحة أسماء شبكية معزولة.

**Blast Radius عند اختراق عامل الفحص:** لا وصول إلى قاعدة البيانات، ولا إلى المخزن النهائي، ولا إلى ملفات مكاتب أخرى (العامل يرى بايتات ملف واحد فقط في ذاكرته المؤقتة)، ولا إلى الأسرار (لا مفاتيح داخل العامل — التوقيع يتم في البوابة)، ولا إلى واجهات داخلية، ولا إلى خدمة بيانات السحابة. أقصى ضرر ممكن: **إفساد نتيجة فحص ملف واحد**، وهو مكشوف لأن القرار يُتخذ في مِهلة بعد التحقق من التوقيع والبصمة.

## 3. EPHEMERAL WORKER MODEL
| | عمّال دائمون | **عمّال مؤقتون معاد تدويرهم (المختار)** |
|---|---|---|
| الأمن | تلوث متبادل بين الملفات، استمرارية الاستغلال | حالة نظيفة لكل ملف تقريباً |
| الأداء | أسرع بدءاً | تكلفة تدوير بسيطة |
| التكلفة | أقل | أعلى قليلاً |
| التعقيد التشغيلي | أقل | متوسط |

**التصميم:** حوض عمّال جاهز (warm pool) بحيث **يُهدم العامل ويُعاد إنشاؤه بعد كل مهمة فحص**، أو بعد 10 مهام كحد أقصى للملفات منخفضة الخطورة، أو فوراً عند: انتهاء المهلة، أو تعطل المحلل، أو أي كشف خبيث. هذا يجمع الأداء المقبول مع منع استمرار أي استغلال بين الملفات.

## 4. NETWORK ISOLATION
**SCANNER_NETWORK_ALLOWLIST**
- بوابة الماسح ← مِهلة (`https` صادر إلى نطاق واحد محدد، mTLS).
- بوابة الماسح ← عامل الفحص (شبكة داخلية خاصة، منفذ واحد).
- عامل الفحص ← **لا شيء** (بلا صادر إطلاقاً؛ يستقبل البايتات من البوابة عبر stdin/مجلد tmpfs).
- تحديث التواقيع: مضيف تحديث منفصل بالكامل، لا يشارك العمّال شبكتهم، ويوزّع الحزم المتحقق منها كصور/أحجام ملفات للقراءة فقط.

**SCANNER_EGRESS_DENY_POLICY:** `DEFAULT DENY` لكل الصادر · بلا DNS للعمّال (منع تسريب DNS) · حجب `169.254.169.254` وكل نطاقات بيانات السحابة وواجهات مستوى التحكم على مستوى الشبكة لا التطبيق · حجب النطاقات الخاصة الأخرى · بلا اتصالات صادرة من المحللات مهما كان محتوى الملف · رصد وتنبيه على أي محاولة صادرة (مؤشر اختراق مباشر).

## 6. SCANNER SUPPLY-CHAIN SECURITY
تثبيت الصور بالـ digest لا بالوسم · صور موقّعة والتحقق من التوقيع عند التشغيل · SBOM لكل بناء · فحص ثغرات للصور والتبعيات في CI · تثبيت التبعيات بقفل · تتبّع إصدارات ClamAV و YARA والمحللات وتسجيلها مع كل قرار · تحديثات مرحلية (canary) قبل التعميم · إمكانية رجوع فوري إلى الـ digest السابق · إثبات مصدر البناء (provenance) · مستودعات حزم موثوقة فقط. **لا تحديث ماسح أو قواعد يصل إلى الإنتاج بلا اجتياز مسار التحقق.**

## 7. SIGNATURE / RULE UPDATE PIPELINE
```text
DOWNLOAD → VERIFY (توقيع المزوّد + بصمة) → TEST (مجموعة عينات ثابتة: نظيفة/EICAR/عينات معروفة)
 → STAGING (تشغيل ظلّي على عيّنة إنتاج مجهولة الهوية) → SECURITY VALIDATION (عتبة إيجابيات كاذبة)
 → PRODUCTION (canary ثم تعميم) → تسجيل إصدار جديد للسياسة
```
الحمايات: رفض أي حزمة قواعد غير موقّعة · مقارنة معدل الكشف قبل وبعد (ارتفاع مفاجئ = انفجار إيجابيات كاذبة ⇒ إيقاف) · تجميد تلقائي إذا تجاوز الكشف عتبة · رجوع فوري لإصدار سابق · تحديث القواعد **لا يمنح** إعادة تصنيف تلقائية إلى clean، بل يُجدول إعادة فحص.

## 8. SECURE DELIVERY ARCHITECTURE (و حدود الإبطال)
| | A: رابط موقّع مباشر | B: **وسيط تنزيل مُصادق (المختار للمستندات)** | C: تذكرة تسليم أحادية | D: هجين |
|---|---|---|---|---|
| الإبطال الرجعي | مستحيل قبل الانتهاء | فوري | فوري | حسب المسار |
| التدقيق | إصدار فقط | كل عملية تسليم | كل استهلاك | جزئي |
| الأداء | الأفضل | جيد (بث) | جيد | جيد |
| كشف عنوان التخزين | نعم | لا | لا | جزئي |

**المختار: B مع عناصر C** — المتصفح ← تفويض مِهلة ← Release Gate ← بث خادمي ← المتصفح، بتذكرة أحادية الاستخدام وفحص القرار الأمني عند **كل** طلب. حدود Worker: البث بالتدفق (streaming) بلا تحميل الملف كاملاً في الذاكرة يجعل ملفات 20MB عملية؛ ومع ذلك تُقاس الكلفة في S3 قبل التعميم. التسليم المباشر بالرابط الموقّع يبقى فقط للمسارات منخفضة الحساسية (وسائط الصفحة العامة بعد الفحص).

**النافذة التي لا يمكن إلغاؤها:** أي رابط موقّع سبق إصداره يبقى صالحاً حتى انتهائه (≤ 60 ثانية)، وأي بايتات وصلت المتصفح لا يمكن استرجاعها. لذلك: `SIGNED_URL_REVOCATION_GUARANTEED = NO`، والحد الأدنى للنافذة مع الوسيط = صفر لطلبات جديدة، ونافذة الاتصال الجاري فقط (تُقطع بإنهاء التدفق).

## 9. SECURE SCAN JOB QUEUE
كل مهمة: `job_id, scan_id, organization_id, object_key, sha256, created_at, expires_at, attempt, policy_version, idempotency_key`. الضوابط: فهرس فريد على `idempotency_key` يمنع المعالجة المكررة · التحقق من انتماء `object_key` للمكتب قبل التنفيذ · nonce وطابع زمني يمنعان إعادة الإرسال · ربط النتيجة بـ `job_id + sha256` يمنع استبدال المهمة · انتهاء صلاحية المهمة يعيدها للجدولة لا للتحرير · حدود عمر ومحاولات.

## 10. CONCURRENCY, TRANSACTIONS & RECONCILIATION
**انتقال الحالة بمقارنة-وتبديل في قاعدة البيانات:** `UPDATE secure_files SET state=:next, version=version+1 WHERE id=:id AND state=:expected AND version=:v` — صفر صفوف يعني أن طرفاً آخر سبقك، فتتوقف العملية. هذا يمنع: فاحصَين لنفس الملف، عاملَي تحرير، إعادة فحص أثناء التحرير، تحرير أثناء إعادة تصنيف خبيث، حذف أثناء الفحص، Override أثناء إعادة فحص. لا اعتماد على أقفال في ذاكرة التطبيق.

**نموذج التحرير الذرّي (Outbox + مصالحة):**
```text
1) تسجيل نية التحرير (release_pending) في معاملة واحدة مع سجل outbox
2) نسخ متكافئ (idempotent) إلى مفتاح نهائي مشتق حتمياً من scan_id
3) التحقق من HASH_AFTER_RELEASE
4) تثبيت released في معاملة تستهلك سجل outbox
فشل بعد الخطوة 2 وقبل 4 ⇒ الكائن النهائي موجود لكن غير مُسجَّل ⇒ غير قابل للوصول
   (البوابة تشترط سجلاً بحالة released) ⇒ عامل المصالحة ينظّفه أو يكمله
```
النتيجة: `DB_RELEASED_BUT_FILE_MISSING` تُكتشف وتُعالج، و`FILE_IN_FINAL_STORAGE_BUT_UNTRACKED` **غير قابل للوصول بحكم التصميم** لأن التسليم يبدأ من السجل لا من التخزين.

**عامل المصالحة الدوري** يقارن: حالة قاعدة البيانات، كائنات الحجر، الكائنات النهائية، البصمات، القرارات الحالية. أي فرق ⇒ `FILE_SECURITY_RECONCILIATION_INCIDENT`: محرَّر بلا كائن · كائن نهائي بلا سجل · بصمة تغيّرت · يتيم في الحجر · عالق في `scanning` · عالق في `releasing`.

## 11. LEGACY ENFORCEMENT STRATEGY
| | A: حجب فوري لكل القديم | **B: فحص مسبق قبل الفرض (المختار)** | C: قبول مخاطرة مؤقت |
|---|---|---|---|
| الأمن | الأعلى | عالي جداً | ضعيف |
| أثر التشغيل | تعطيل مكاتب عاملة | شبه معدوم | معدوم |
| التوافق مع الهدف | نعم | نعم | لا |

الترتيب: جرد كامل ← حساب البصمات ← تصنيف المخاطر ← **فحص كل الملفات القابلة للوصول قبل تفعيل الفرض** ← تفعيل الفرض فقط بعد بلوغ backlog صفر للملفات عالية ومتوسطة الخطورة. أي استثناء متبقٍّ (ملف تالف أو غير قابل للفحص) يُحجب لا يُستثنى. لذلك: **LEGACY_UNSCANNED_ACCESS_AFTER_ENFORCEMENT = NO**. أي قبول مخاطرة مستقبلي يجب أن يكون صريحاً ومحدد المدة وموثقاً وقابلاً للقياس ومعتمداً من مالك المنصة — ولا يُقبل كسلوك افتراضي مخفي.

## 12. MALICIOUS & OVERRIDE POLICY
- **خبيث مؤكد:** لا عودة إلى مساحة العمل ولا بوابة العميل ولا تنزيل عادي، بأي صلاحية. المسار الوحيد هو خزنة الأدلة الأمنية عبر مسار حادث. `MALICIOUS_NORMAL_DELIVERY = IMPOSSIBLE` مفروضة بقيد قاعدة بيانات على الانتقالات لا بمنطق تطبيق فقط.
- **اختلاف البصمة:** لا Override لأي أحد بما فيهم مالك المنصة. الحل الوحيد: رفع جديد ← كائن جديد ← فحص جديد ← بصمة جديدة.
- **مشبوه — مستويات مخاطر:** منخفض (مراجع أمني واحد + سبب + تدقيق) · متوسط (مراجع + مصادقة تصعيدية MFA) · مرتفع (موافقة مزدوجة + مهلة تبريد + مراجعة بعد الفحص بمحرك مُحدَّث). أي Override يولّد **قراراً أمنياً جديداً** ولا يعدّل أو يحذف القرار السابق إطلاقاً.

## 13. IMAGE SECURITY ARCHITECTURE
الصور مسار مستقل: تحقق من البصمة والأبعاد (حد 12000×12000 بكسل) ونسبة البكسل إلى البايت (كشف قنابل فك الضغط) وسلامة البنية · **فك ترميز وإعادة ترميز إجبارية** لكل صورة تُعرض، مع تجريد كامل لبيانات EXIF وملفات ICC والبيانات المضمّنة (تحمي من استغلال المحلل عند العميل ومن تسريب الموقع الجغرافي) · رفض الصور المشوّهة · كشف Polyglot (صورة تحوي ZIP أو HTML) · HEIC غير مدعوم حالياً ويبقى مرفوضاً · **SVG: منع كامل** — محتوى نشط بطبيعته ولا مبرر قانوني لقبوله؛ إن طُلب مستقبلاً فبتحويله إلى PNG خادمياً لا بتعقيمه. فك الترميز يجري داخل منطقة المعالجة العدائية لا داخل التطبيق.

## 14. PUBLIC OFFICE MEDIA (أعلى حساسية)
`office-public-media` هي الوجهة العامة الوحيدة، لذا الانتقال `draft → public` يصبح مساراً محكوماً: فحص كامل ← تحقق بنيوي ← إعادة ترميز آمنة وتجريد البيانات الوصفية ← قرار أمني ← تحرير. لا نسخ إلى المخزن العام بلا `released`. الهدف: **UNSCANNED_PUBLIC_MEDIA = 0**. ترويسات التقديم تبقى `nosniff` مع نوع محتوى مثبّت من الفحص لا من قاعدة البيانات.

## 15. CDR — DELIVERY & ISOLATION
- **SANITIZED_DEFAULT_DELIVERY**: كل عرض وتنزيل عادي داخل المنصة وبوابة العميل يستخدم المشتق المطهّر.
- **ORIGINAL_RESTRICTED_EVIDENCE_ACCESS**: الأصل يُحفظ للقيمة الإثباتية، ولا يُسلَّم إلا بصلاحية مستقلة + مصادقة تصعيدية + سبب إلزامي + تحذير صريح + حدث تدقيق + سقف زمني. الأصل الذي أُزيل منه محتوى نشط لا يُسلَّم للاستخدام اليومي إطلاقاً.
- محرك CDR يعمل داخل نفس منطقة المعالجة العدائية بعزل مطابق للماسح، ولا يُستدعى كمكتبة داخل عملية التطبيق أبداً. فشل CDR ⇒ `unscannable` لا تسليم للأصل.

## 16. TAMPER-EVIDENT AUDIT
أبسط تصميم قوي وقابل للتشغيل: **سلسلة بصمات على مستوى الحدث** (`event_hash = SHA256(prev_hash || canonical_payload)`) مع `sequence` فريد لكل مكتب، ثم **ملخّص يومي موقّع** بمفتاح غير موجود في قاعدة البيانات (KMS)، ثم نسخ الملخّص اليومي إلى مخزن خارجي للقراءة فقط (WORM). أي تعديل أو حذف تاريخي يكسر السلسلة ويظهر في التحقق اليومي التلقائي. لا حاجة لأي حل موزّع. **AUDIT_LOG_TAMPER_EVIDENT = YES.**

## 17. PLATFORM SECURITY vs TENANT PRIVACY
البحث عن نفس البصمة عبر المكاتب مسموح **لخدمة أمن المنصة فقط** عبر صلاحية مستقلة `platform_security.ioc_search`، بسبب مسجّل وتدقيق كامل، ونتائج مجمّعة لا تكشف هوية المكاتب إلا داخل مسار حادث معتمد. لا مكتب ولا مدير عادي يعرف أن نفس الملف موجود لدى غيره. **CROSS_TENANT_FILE_LEAKS = 0** هدفاً.

## 18. SECRET / KMS MODEL
مفاتيح mTLS الخاصة وأسرار HMAC واعتمادات الماسح ومفاتيح التوقيع ومفاتيح توقيع قواعد YARA: تُحفظ في مدير أسرار/KMS، لا في الشيفرة ولا في قاعدة البيانات كنص صريح ولا في الواجهة. توزيع للذاكرة فقط عند الإقلاع، دوران كل 90 يوماً مع فترة تداخل، فصل تام بين البيئات، تدقيق كل وصول، وإجراء إبطال طارئ موثّق يمكن تنفيذه خلال دقائق.

## 19. ENVIRONMENT SEPARATION
ماسح التطوير والتجربة والإنتاج: اعتمادات وشهادات وطوابير ومخازن وسياسات منفصلة. **ماسح التطوير لا يملك أي مسار تقني لقراءة مستندات الإنتاج**، ويُثبت ذلك باختبار سلبي دوري.

## 20. LOG REDACTION POLICY
قائمة سماح لحقول السجل: `scan_id, job_id, organization_id (معرّف فقط), sha256, extension, size, engine+versions, verdict, duration, error_code`. ممنوع: محتوى المستند أو نصه، اسم الملف الكامل للعميل (يُختصر ويُهشَّم)، الرموز والتذاكر، الروابط الموقّعة، المفاتيح الخاصة، أي بيانات شخصية. تنقيح إجباري في طبقة التسجيل نفسها لا بالاعتماد على المطور.

## 21. ABUSE / COST DoS PROTECTION
حدود لكل مستخدم (60 ملفاً/ساعة) ولكل مكتب (500 ملف و2GB/ساعة، قابلة للرفع بالباقة) · حد تزامن فحص لكل مكتب (5) · حد طول الطابور لكل مكتب · حد فتحات الرفع المفتوحة · كشف إساءة عند تكرار الفشل أو الكشف الخبيث (تشديد تلقائي وتنبيه) · حصص متدرجة حسب الباقة حتى لا تتأثر المكاتب الشرعية.

## 22. RESOURCE LIMITS داخل محركات الفحص
ClamAV: `MaxScanSize=64M, MaxFileSize=20M, MaxRecursion=4, MaxFiles=200, MaxScanTime=30s, MaxEmbeddedPE`, تعطيل الفحوص غير اللازمة. YARA: مهلة 10 ثوانٍ لكل ملف، حد حجم القواعد، حد المطابقات. استخراج الأرشيف: عمق 2، 200 ملف، 200MB مستخرجة، نسبة ≤ 100:1. CDR: مهلة 20 ثانية، ذاكرة 256MB. المحللات البنيوية: مهلة 8 ثوانٍ، 50k كائن، 2000 صفحة، منع كيانات XML كلياً. تجاوز أي حد ⇒ `unscannable`، ولا يُعد نجاحاً أبداً.

## 23. MIME DETECTION
كشف مستقل حقيقي (مكافئ libmagic + محاولة تحليل فعلي) وليس اشتقاقاً من الامتداد. تُقارَن خمسة مصادر: الامتداد، النوع المُعلن، النوع المكتشف، بصمة البايتات، ونتيجة المحلل. أي تعارض ⇒ `suspicious` على الأقل. **كشف Polyglot صريح**: وجود أكثر من توقيع صيغة معروف داخل الملف، أو بنية صالحة لأكثر من صيغة، ⇒ حظر مباشر.

## 24. ENCRYPTED / PASSWORD-PROTECTED FILES
سياسة نهائية: **UNSCANNABLE ⇒ BLOCK** ولا تسليم إطلاقاً. لا تُبنى أي آلية لجمع كلمات مرور المستندات. رسالة عربية واضحة تطلب رفع نسخة غير محمية. لا يوجد مسار يجعل ملفاً غير قابل للفحص يظهر كـ clean.

## 25. SECURITY DECISION SEMANTICS
لا تُستخدم كلمة SAFE. القرار يُصاغ: `CLEAN_UNDER_POLICY_vX (engine=…, av_sig=…, yara=…, structural=…, decided_at=…)`. ويصاحبه دائماً معنى صريح: «لم يُكتشف تهديد وفق سياسة الإصدار X في هذا التاريخ»، وهو قابل للنقض بإعادة فحص لاحقة.

## 26. FALSE POSITIVE WORKFLOW
بلاغ إيجابية كاذبة ⇒ إعادة فحص بمحرك وقواعد محدّثة ⇒ مراجعة بمحرك ثانٍ أو قاعدة مستقلة إن توفر ⇒ مراجعة أمنية بشرية ⇒ **قرار جديد** يُضاف. نتيجة الكشف الأصلية تبقى محفوظة إلى الأبد. لا يتحول هذا المسار إلى Override سهل: لا يمر عبر المكتب بل عبر أمن المنصة.

## 27. MULTI-ENGINE STRATEGY
**مبرَّر** للملفات عالية الخطورة فقط (Office بماكرو، PDF بمحتوى نشط، ملفات من بوابة العميل غير الموثوقة، أي ملف بعد بلاغ حادث). **غير مبرَّر** للصور ونصوص PDF البسيطة والمستندات الداخلية منخفضة الخطورة. يُضاف كطبقة انتقائية لاحقة لتفادي مضاعفة الكلفة بلا داعٍ.

## 28. SECURITY EVIDENCE VAULT
مخزن رابع منفصل تماماً للملفات الخبيثة المؤكدة وعينات التحقيق والأصول الجنائية: معزول، غير قابل للتنزيل من أي مكتب، غير مفهرس ولا قابل للبحث في التطبيق، ممنوع على الذكاء الاصطناعي والـOCR، مدقَّق بصرامة، بمفاتيح وصلاحيات مستقلة، وسياسة احتفاظ محددة (مقترح 90 يوماً ثم حذف موثّق) وبلا أي مسار يعيده إلى مسار التسليم العادي.

## 29. FILE LIFECYCLE & RETENTION
`Upload → Quarantine → Scan → Decision → Release → Use → Rescan → Reclassify → Block → Retention → Delete`. سياسات الحذف: سجل قاعدة البيانات (حذف منطقي ثم فعلي بعد فترة) · الكائن النهائي (حذف فوري عند طلب المكتب) · المشتق المطهّر (يتبع الأصل) · نسخة الحجر (تُحذف بعد التحرير الناجح أو تنتقل للخزنة عند الخبث) · بيانات الفحص (تبقى للتاريخ الأمني بلا محتوى) · سجل التدقيق (**لا يُحذف أبداً**). أي احتفاظ قانوني إلزامي يعلو على طلب الحذف ويُبلَّغ به المكتب.

## 31. SECURITY CI/CD GUARDRAILS
يفشل البناء عند اكتشاف: مسار رفع مباشر جديد · تنزيل من التخزين خارج البوابة · إصدار رابط موقّع خارج البوابة · معالج ملفات جديد بلا Release Gate · تعامل جديد مع مخزن عام · تحديث حالة خارج دالة الانتقال المعتمدة · دالة إدخال لا تستخدم `ingestFile()` · تسجيل حقول خارج قائمة السماح · أي مرجع لمفتاح سرّي في الشيفرة.

## 32. CHAOS / FAILURE TESTING
قتل الماسح أثناء الفحص · قتل عامل التحرير أثناء النسخ · انقطاع قاعدة البيانات بعد نسخ التخزين · مهلة تخزين بعد القرار · Callback مكرر · Callback خارج الترتيب · اعتماد ماسح منتهٍ · شهادة mTLS غير صالحة · تكرار في الطابور · إعادة إرسال من الطابور · محاكاة ماسح مخترق (نتائج موقّعة بمفتاح خاطئ أو ببصمة ملف آخر) · تغيّر سياسة الأمن أثناء الفحص · إعادة فحص تصنّف ملفاً محرَّراً كخبيث أثناء محاولة تنزيل جارية. كل سيناريو يجب أن ينتهي بحالة رفض صريحة أو مصالحة نظيفة. بلا برمجيات خبيثة حقيقية — EICAR وعينات اصطناعية فقط.

## 33. FINAL ARCHITECTURE COMPARISON
| المعيار | A: Lovable فقط | **B: Lovable + منطقة معالجة عدائية سعودية مُحصَّنة** | C: بنية سعودية كاملة |
|---|---|---|---|
| الأمن بعد متطلبات V3 | غير كافٍ (بلا AV ولا YARA ولا عزل) | عالٍ جداً | عالٍ جداً |

## 34. SCANNER HIGH AVAILABILITY
بوابتان على الأقل خلف موازن · حوض عمّال ≥ 2 مع تدوير · طابور دائم يحفظ المهام عند التعطل · فحوص صحة (حيّ/جاهز) وإخراج العقدة المعطوبة تلقائياً · تجاوز فشل تلقائي · نطاقا توفر إن سمحت البنية.
**أهداف داخلية (ليست SLA تعاقدية):** توفر بوابة الماسح ≥ 99.5% شهرياً · استرجاع الطابور بعد تعطل ≤ 5 دقائق بلا فقد مهام · أقصى تراكم مقبول 500 مهمة أو 30 دقيقة انتظار · تنبيهات: تراكم > 200 أو انتظار > 10 دقائق (تحذير)، تعطل بوابة > 2 دقيقة أو تراكم > 500 (حرج)، عمر التواقيع > 48 ساعة (حرج).

## 35. RESIDUAL RISKS
ثغرات Zero-day لا تكشفها التواقيع · مستند سليم تقنياً واحتيالي المحتوى · البايتات التي وصلت المتصفح قبل إعادة التصنيف لا تُسترجع · إساءة مستخدم مخوَّل · تلوث سلسلة توريد القواعد رغم الضوابط · تعطل الماسح يعطّل الرفع (مقايضة مقصودة) · كلفة وأداء الوسيط للملفات الكبيرة تحتاج قياساً فعلياً.
