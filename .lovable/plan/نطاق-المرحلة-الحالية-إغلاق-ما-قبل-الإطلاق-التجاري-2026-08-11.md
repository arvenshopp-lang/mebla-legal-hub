# نطاق المرحلة الحالية — إغلاق ما قبل الإطلاق التجاري

خطة مبنية على فحص فعلي للكود وقاعدة البيانات في هذا المشروع. لا ميزات مستقبلية، ولا جداول أو خدمات مكرّرة.

## 1) جدول حالة الوحدات (نتيجة الفحص الفعلي)

| الوحدة | البنية الحالية | الحالة |
| --- | --- | --- |
| التسجيل/الدخول/MFA/OTP | `login/register/reset` + `sms/otp.server.ts` + `mfa.ts` | مبني ومراجع بالكود، اختبار E2E جزئي (`plan7_user_lifecycle`) |
| Onboarding والعضويات | `onboarding.tsx` + `organization_members` + `_authenticated/route.tsx` | مبني، E2E جزئي |
| لوحة التحكم/العملاء/القضايا/الجلسات/المهل/المهام/المستندات/الفريق/الإعدادات | `src/routes/_authenticated/*` + `DataView` | مبني ومراجع، E2E سابق للمرحلتين A/B/C فقط — يحتاج إعادة تشغيل شاملة |
| العروض والعقود والقوالب | `sales-docs.functions.ts` (20 دالة) + `sales_documents/_items/_templates/_signatures` | مبني — يوجد بلاغ «تعذّر الإنشاء» غير مُعاد إنتاجه بعد، السبب غير مؤكد |
| التوقيع الإلكتروني | `salesSign` + `sales_document_signatures` (توقيع داخلي بـ SHA-256) | مبني داخلياً — لا توجد طبقة Provider Adapter لمزوّد خارجي |
| الفوترة والدفع | `billing/providers.server.ts` (`manual` + `moyasar`) + `webhooks.server.ts` + خزانة مشفّرة | مبني ومراجع بالكود — لم يُختبر مع مفاتيح حقيقية (Sandbox/Production) |
| الإشعارات | `notifications/engine.server.ts` + `queue.server.ts` + `notification_rules` | مبني — القاعدة تحتوي حالياً نوعاً واحداً فقط `hearing_reminder`، ولا مادة تذكير للمهل ولا المهام المتأخرة |
| البريد الرسمي | `email/*` + Hostinger + قوالب RTL | مبني، E2E سابق للوارد والصادر |
| WhatsApp | `notifications/whatsline.server.ts` | موصل جاهز للربط — غير مُثبت الاتصال بمزوّد فعلي |
| بوابة العميل | `client-portal.functions.ts` (رفع بتوكن + `lookupCaseStatus`) + `track.tsx` | ناقصة: لا فواتير ولا تحديثات ولا طلبات توقيع للعميل |
| استيراد CSV للعملاء/القضايا | غير موجود (يوجد تصدير CSV فقط) | فجوة |
| تقارير تشغيلية للمكتب | `kpi/*` + `team-performance` | جزئي — لا صفحة تقارير تشغيلية موحّدة |
| RLS/RBAC/التدقيق/التخزين الخاص | `security-guardrails*`، `sensitive-guard.server.ts`، Signed URLs | مبني ومُحرَّس — يحتاج إعادة إثبات E2E في هذه المرحلة |

## 2) الأعطال والفجوات مرتبة بالأولوية

P0 — حاجب للإطلاق
1. «تعذّر الإنشاء» في العروض/العقود/القوالب: يجب إعادة إنتاجه فعلياً (Playwright + سجلات دوال الخادم) ثم إصلاح السبب الجذري. لن يُعلن مغلقاً بدون رحلة ناجحة موثّقة.
2. لا إثبات E2E حديث للرحلات الأساسية العشر بعد آخر تغييرات النماذج والتنسيق.
3. الدفع عبر ميسر بلا اختبار اتصال حقيقي — يبقى «غير حي» حتى Sandbox ثم Production.

P1 — نطاق الميزات
4. بوابة العميل لا تعرض الفواتير ولا التحديثات ولا طلبات التوقيع.
5. لا طبقة Provider Adapter للتوقيع الإلكتروني الخارجي.
6. لا تذكيرات للمهل ولا للمهام المتأخرة في محرّك الإشعارات.
7. لا استيراد CSV للعملاء والقضايا.
8. لا صفحة تقارير تشغيلية للمكتب.

P2 — إثبات أمني
9. إعادة تشغيل مصفوفة العزل/RBAC/IDOR/Signed URLs/SECURITY DEFINER/Audit مع دليل نتائج.
10. تدقيق الجوال وRTL على المسارات المتأثرة بتغييرات النماذج الأخيرة.

## 3) خطة التنفيذ (مراحل، كل مرحلة تُغلق بدليل)

- المرحلة 0 — تشخيص: إعادة إنتاج عطل العروض/القوالب، وجمع سجلات دوال الخادم، وتقرير سبب جذري مكتوب قبل أي تعديل.
- المرحلة 1 — إصلاح العروض والعقود والقوالب: إصلاح السبب الجذري داخل `sales-docs.server.ts`/`sales-docs.functions.ts`، وربط كل مستند بالقضية أو العميل عبر الأعمدة القائمة في `sales_documents`، ورسائل عربية دقيقة بدل «تعذّر الإنشاء».
- المرحلة 2 — بوابة العميل الآمنة: توسيع `client-portal.functions.ts` و`track.tsx` بدوال قراءة خادمية مقيّدة بالتوكن تعرض: قضايا العميل، تحديثاته من `case_updates`، مستنداته المصرّح بها، فواتيره من `invoices`، وطلبات توقيعه من `sales_document_signatures`. لا جداول جديدة، ولا كشف ملاحظات داخلية، وكل قراءة تُسجَّل في سجل الوصول القائم.
- المرحلة 3 — طبقة التوقيع الإلكتروني: عقد `SignatureProvider` بنفس نمط `billing/providers.server.ts` مع مزوّد `internal` الحالي كتطبيق أول، وحالة `not_configured` صادقة لأي مزوّد خارجي قبل حفظ مفاتيحه ونجاح اختبار الاتصال.
- المرحلة 4 — الدفع عبر ميسر: إكمال دورة Sandbox عبر مركز المزوّدين القائم (اختبار اتصال، إنشاء دفعة، ويبهوك موقّع، تحقق مبلغ وعملة، استرداد)، ثم لا يُفعّل الإنتاج إلا بمفاتيح حقيقية واختبار ناجح.
- المرحلة 5 — التذكيرات: إضافة أنواع أحداث للمهل والجلسات والمهام المتأخرة داخل `engine.server.ts` و`notification_rules` القائمين، مع منع التكرار عبر البصمة الحالية، وتشغيلها من مسار الـ hooks الموجود. لا Workflow Builder.
- المرحلة 6 — استيراد CSV: دالة خادمية واحدة لكل من العملاء والقضايا بمعاينة قبل التنفيذ، وتقرير أخطاء بالسطر، ومنع تكرار (الهوية/الجوال للعملاء، رقم القضية للمكتب)، وحد أقصى للحجم والصفوف، وعزل صارم بمعرّف المكتب، وسجل تدقيق للعملية.
- المرحلة 7 — تقارير تشغيلية: صفحة واحدة تعيد استخدام محرّك `kpi` الحالي (القضايا حسب الحالة، الجلسات القادمة، المهل المستحقة، المهام المتأخرة، أحمال الفريق) بتصدير CSV/PDF بالبنية القائمة.
- المرحلة 8 — الإثبات النهائي: تشغيل مصفوفة الاختبار كاملة وتقرير نتائج قابل للمراجعة في `docs/qa/`.

## 4) ما يحتاج خطوة يدوية منك

- مفاتيح ميسر Sandbox ثم Production (تُحفظ في خزانة التكاملات، لا في الكود).
- قرار مزوّد التوقيع الإلكتروني ومفاتيحه — قبل ذلك تبقى الطبقة `not_configured`.
- بيانات Whats Line والقوالب المعتمدة لتشغيل WhatsApp فعلياً.
- تأكيد جاهزية بريد `mail.mehlalex.com` للاختبار الحي.
- حساب/بيانات QA معزولة للاختبار الحي على الإنتاج.

## 5) مصفوفة اختبار E2E

- الرحلات: تسجيل، تحقق، دخول، onboarding، إنشاء عميل، إنشاء قضية، جلسة، مهلة، مهمة، رفع مستند، دعوة عضو، تعديل إعدادات.
- العروض والعقود: إنشاء مسودة، حفظ قالب، اعتماد، إرسال، PDF، تحويل لفاتورة، توقيع.
- بوابة العميل: توكن صالح، توكن منتهي، توكن مكتب آخر (يجب الرفض)، عدم ظهور ملاحظات داخلية أو مستندات غير مصرّحة.
- الصلاحيات: مصفوفة الأدوار الخمسة على كل دالة خادمية حساسة، ومحاولات تصعيد صلاحية.
- العزل وIDOR: قراءة/كتابة بمعرّفات مكتب آخر لكل وحدة، وSigned URLs منتهية أو مبدّلة.
- الفوترة: ويبهوك بتوقيع خاطئ، مبلغ مختلف، عملة مختلفة، حدث مكرر، استرداد يتجاوز المدفوع، فترة مالية مقفلة.
- الاستيراد: ملف كبير، صيغة خاطئة، صفوف مكرّرة، حقول ناقصة، محاولة حقن صيغ.
- التذكيرات: استحقاق، تكرار، فشل مزوّد، إعادة محاولة، dead_letter.
- الجوال وRTL: iPhone وiPad وسطح المكتب لكل مسار — لا تمرير أفقي، أهداف لمس ≥44px، Bottom Sheets.
- حالات الفشل: انقطاع الشبكة، ضغط مزدوج، فشل حفظ مع بقاء بيانات النموذج، رسائل عربية دون كشف أسرار.

## ملاحظات تقنية

كل قراءة أو كتابة تمر عبر `createServerFn` مع `requireSupabaseAuth` أو حرس التوكن للبوابة العامة، وتُعاد استخدام `sensitive-guard.server.ts` وسجلات التدقيق القائمة. لا `supabaseAdmin` لقراءات عادية. أي تغيير قاعدة بيانات يكون Migration توافقية مع GRANT وRLS، ولا يُعلن أي بند مكتملاً بدون دليل اختبار في `docs/qa/`.
