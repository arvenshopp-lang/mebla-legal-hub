# # خطة تنفيذ مضبوطة: استعادة المعاينة ثم اختبار Design Studio فعلياً

## الهدف

التعامل مع خطأ Preview Storage `403 AccessDenied` دون تغيير عشوائي في المشروع، ثم اختبار تغييرات Design Studio فعلياً في المتصفح قبل اعتمادها.

## قواعد ملزمة

- لا تنفذ أي Fix أو تعديل كود أو CSS أو Migration أو RLS أو GRANT أو Secrets أو إعدادات تخزين بهدف معالجة خطأ 403.

- لا تنشئ “تعديلاً تافهاً” أو تحفظ ملفاً فقط لإجبار Build جديد.

- لا تعتبر Build أو TypeScript أو ESLint أو تشغيل localhost دليلاً على نجاح الواجهة أو الصلاحيات.

- لا تستخدم Mock أو Session اصطناعية أو تعديل Local Storage كدليل للاختبارات.

- لا تمس بيانات العملاء أو القضايا أو المستندات أو حسابات الموظفين الحقيقية.

- لا تنفذ Publish أو Rollback على بيئة مرتبطة بالإنتاج إلا بعد التحقق أن الاختبار معزول ولا سيغير مظهر الإنتاج أو بياناته.

## 1. محاولة معاينة واحدة فقط

1. تحقق من أن حالة Lovable لا تعرض Incident مفتوحاً متعلقاً بالـ Editor أو Hosting أو Preview.

2. سجّل قبل المحاولة:

   - الوقت UTC

   - Project ID

   - Build / Deployment ID الجديد إن ظهر

3. نفّذ محاولة واحدة فقط عبر زر Retry أو Redeploy أو Preview الرسمي في Lovable.

4. لا تغيّر أي ملف أو إعداد قبل المحاولة أو خلالها.

### قرار النتيجة

- إذا عاد `403 AccessDenied`:

  - توقف فوراً.

  - لا تنفذ أي Fix داخل المشروع.

  - قدّم تقريراً مختصراً يحتوي نص الخطأ كاملاً والوقت UTC وProject ID وBuild/Deployment ID.

  - جهّز نص تذكرة دعم Lovable، ولا تنتقل إلى اختبارات Design Studio.

- إذا فتحت المعاينة:

  - انتقل مباشرة إلى الاختبارات أدناه.

  - لا تعتبر المهمة ناجحة قبل اكتمالها بالأدلة.

## 2. حماية بيئة الاختبار

قبل أي اختبار كتابة أو نشر:

1. تحقّق هل المعاينة تستخدم قاعدة بيانات أو إعدادات مشتركة مع الإنتاج.

2. إذا كانت مشتركة مع الإنتاج:

   - لا تختبر نجاح Publish أو Rollback أو أي تعديل مرئي للمظهر العام.

   - نفّذ فقط اختبارات القراءة والمنع والصلاحيات التي لا تغيّر بيانات.

   - أبلغني صراحة أن اختبار النشر يحتاج بيئة Staging أو قاعدة بيانات معزولة.

3. إذا كانت بيئة الاختبار معزولة:

   - استخدم حسابات اختبار حقيقية مخصصة فقط، لا حسابات العملاء أو الشركاء.

   - استخدم CSS تجريبياً غير مؤثر وواضح، ثم نظّف بيانات الاختبار بعد الانتهاء.

4. لا تعدّل صلاحيات حساب حقيقي فقط من أجل الاختبار.

## 3. اختبار Design Studio الفعلي

نفّذ الاختبارات من المتصفح وعلى الواجهة الحقيقية، مع توثيق:

- الرابط أو الصفحة المختبرة

- الدور المستخدم

- النتيجة الفعلية

- لقطة شاشة عند الحاجة

- نتيجة طلب الخادم للحالات الحساسة، بما فيها رمز الاستجابة 403 عند الرفض

| الحالة | النتيجة المطلوبة |

|---|---|

| فتح المعاينة | الصفحة الرئيسية تعمل بلا أخطاء Console حرجة |

| Super Admin يفتح `/mehla-admin/design` | يظهر المحرر الحقيقي والسجل والإصدارات، وليس Mock UI |

| Super Admin يحفظ Draft | ينجح مع إصدار/مراجعة وسجل تدقيق فعلي |

| معاينة Draft | تظهر داخل المعاينة فقط ولا تظهر في نافذة إنتاج مستقلة |

| Super Admin ينشر CSS تجريبياً | ينفذ فقط في بيئة معزولة، مع ثبات النتيجة بعد Refresh |

| Super Admin يعمل Rollback | ينشئ إصداراً جديداً ولا يحذف تاريخ الإصدارات |

| Platform Designer: قراءة وحفظ Draft ومعاينة | تنجح ضمن صلاحياته |

| Platform Designer: Publish وRollback من الواجهة | الأزرار غير متاحة أو معطلة بسبب واضح |

| Platform Designer: طلب Publish وRollback مباشر للخادم | رفض خادمي فعلي `403` أو ما يعادله برسالة عربية، مع Audit Log لمحاولة الرفض |

| مستخدم عادي بلا صلاحية | لا يصل للرابط أو البيانات أو Server Actions حتى لو استدعى الطلب مباشرة |

| CSS يحتوي `@import` | رفض عربي واضح مع رقم السطر إن كانت القاعدة تدعم ذلك |

| CSS يحتوي رابطاً خارجياً داخل `url()` | رفض وفق سياسة الحارس الحالية مع سبب واضح |

| CSS يخالف قواعد عناصر الأمان | رفض من الخادم، وليس مجرد إخفاء زر في الواجهة |

| CSS فيه خطأ صياغة | رسالة عربية مفهومة مع السطر والعمود إن توفر |

| CSS المنشور الحالي | يقبل عند الحفظ دون Regression من فحص PostCSS AST |

| سجل التدقيق | يسجل الحفظ والنشر والرفض دون كشف بيانات حساسة |

## 4. اختبار الانحدار المرتبط

بعد نجاح اختبارات Design Studio، نفّذ Smoke Test حقيقياً دون تعديل بيانات حقيقية على:

- تسجيل الدخول والخروج.

- Dashboard.

- العملاء.

- القضايا.

- المستندات.

- النماذج والجداول والنوافذ المنبثقة.

- الصلاحيات وعدم ظهور روابط الإدارة للمستخدم العادي.

اختبر العرض على:

- Desktop: 1280px

- Tablet: 834px

- iPhone: 390px

المطلوب:

- لا يوجد تمرير أفقي على مستوى الصفحة.

- لا يوجد قص أو تداخل أو عناصر غير قابلة للضغط.

- أهداف اللمس الأساسية مناسبة للجوال.

- لا توجد أخطاء Console حرجة.

## 5. التعامل مع أي فشل

إذا فشل أي بند:

1. توقف عند الفشل ولا تطبق Fix تلقائياً.

2. حدّد السبب الجذري بالدليل: الصفحة، الدور، الطلب، الاستجابة، والسجل ذي الصلة.

3. وضّح هل العطل:

   - في الواجهة

   - في Server-side authorization

   - في قاعدة البيانات أو Trigger

   - في فحص CSS

   - في بيئة Lovable أو المعاينة

4. قدّم خطة إصلاح واحدة محدودة لأصغر تغيير لازم، مع تحليل Regression على Design Studio والصلاحيات وسجل التدقيق.

5. لا تنفذ الإصلاح إلا بعد موافقة جديدة.

## 6. معيار الإغلاق والتقرير النهائي

لا تعتبر المهمة مكتملة إلا إذا:

- نجحت المعاينة بالمتصفح.

- اجتازت جميع اختبارات الصلاحيات الفعلية، خصوصاً رفض Publish وRollback من الخادم لدور Platform Designer.

- لم يتأثر الإنتاج أو بياناته أثناء الاختبار.

- لا يوجد FAIL مفتوح في اختبارات Design Studio أو Smoke Test.

- تم تنظيف أي بيانات اختبار أُنشئت في بيئة معزولة.

أرسل التقرير النهائي بهذا الشكل:

1. هل نجحت محاولة المعاينة أم لا.

2. البيئة المستخدمة وهل كانت معزولة عن الإنتاج.

3. جدول الاختبارات: الحالة | الدور | النتيجة | الدليل.

4. أي حالات غير قابلة للاختبار ولماذا.

5. قائمة FAIL إن وجدت والسبب الجذري.

6. لا تقترح أو تنفذ أي تعديل إضافي إذا كانت جميع الاختبارات ناجحة.
